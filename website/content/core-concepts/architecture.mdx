## How they fit together

```text
 source.ts ──saykit extract──▶ locales/en.po ──saykit compile──▶ locales/en.js
 (macros)    transformer +     (translators     formatter +       (data your
              formatter         edit these)      ICU compiler       app imports)

 source.ts ──bundler + saykit plugin──▶ say.call({ id: 'Zk1aQv', _name: name })
```

1. **Extract.** The CLI walks each bucket's files, the transformer finds the macros, and the formatter writes the **source** locale's catalogue. Other locales are never touched, so translations are never overwritten.
2. **Compile.** The CLI reads each locale's catalogue, fills untranslated keys from its fallback chain, and compiles every ICU message to data with its number and date formats resolved. `extract` ends by doing this, and `saykit compile` does it alone.
3. **Build.** The plugin rewrites each macro into a `say.call(...)` with the message's id and values. It does nothing else: a locale module is an ordinary `.js` import your bundler already knows how to load, split and hot-reload.

## Identifiers

Every message gets a **6-character hash** of its ICU text and context:

```text
sha256("Hello, {name}!" + context)  →  "Zk1aQv"
```

The same text and context always give the same id, so moving a message between files or reformatting it changes nothing. A [descriptor](/core-concepts/messages#descriptors) can set a readable id instead.

## What ships

- the `saykit` runtime, with no dependencies, and whichever integration you use
- the `say.call(...)` calls the plugin wrote
- the locale modules you import

A locale module is plain data, with nothing left to parse, so the only formatting code that ships is a small evaluator over `Intl`. Being data is also what lets a server hand a locale to a client as JSON. Locales you never import never reach your bundle.
